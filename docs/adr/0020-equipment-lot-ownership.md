# ADR 0020: 装備の個体所有と互換投影

状態: ローカル実装・統合検証中。対象は ITEM-02 / ITEM-03 / ITEM-04 と死亡・保存の整合性。

## 問題

旧形式は所持品・箱・ドロップ・墓標に品目別の個数を持つ一方、品質と耐久を個人×品目、継ぎ装を所有者×品目で持っていた。実際に、品質3・耐久7・火の継ぎ装付き棍棒を受け渡すと受取人側の古い品質/耐久が適用され、継ぎ装は元の所有者に残った。死亡後に同じ武器を先に作ると、新品が墓標の品質/継ぎ装を引き継ぎ、墓標回収後の2本が同じ状態を共有した。

## 正本

`GearContainer = {version:1, revision, lots, activeByKind}` を導入する。

`GearLot = {id, kind, count, quality?, durability?, fusion?, legacy?}` は同じ状態を持つ装備群。通常の新規制作は1本。旧セーブの同種大量所持だけを1件ずつ展開せず `count` で保持する。

- 装備の個数は lots が所有する。従来の `inventory[kind]` は lots の合計への互換投影。
- 品質・耐久の個人辞書、Skybound の fusion 読取は、選択された個体の互換表示。独立した正本にしない。
- `activeByKind` は所持するlot IDを指す。受取りで同種の既存選択を上書きしない。
- 使用・摩耗・修理・強化・合成が旧 `count > 1` の群を変更する場合、選択した1本だけを別IDへ分けてから変更する。
- 一つのlot IDは一つの所有場所にだけ存在する。個人・休眠参加者・両形式の墓標・箱・地面・投擲中を保存時に横断検査する。
- 全量の移動はIDを保つ。一部分だけの移動は新しいIDへ分ける。元の品質・耐久・継ぎ装をそのまま移す。

所有場所は `AdventureSave.gearItems`、`graveGear`、旧墓標の `gearItems`、`BuildingState.gearItems`、`ResourceNode.gearItems`。移動倉庫の装備収納はこの区切りでは有効にしない。

## 予算と失敗時の挙動

- 1つの所有場所は最大128lot。旧1品目の個数上限100,000,000を保持し、個数に比例するオブジェクトへ展開しない。
- 既存の32〜44所持枠、重量、静的な箱10枠を引き続き検査する。
- 地面の装備は一つのlotを持つドロップ。異なる状態の装備を品目名だけで混ぜない。既存の資源ドロップのスタック処理は維持する。
- 明示的な装備移動の個数が既に足りない場合は拒否する。古い要求を小さい個数へ黙って変えない。
- 素材、個数、空き、識別子、metadata予算を先に検査する。候補IDは予約段階では消費せず、成功する同期トランザクションだけがカウンターを進める。
- 失敗した出し入れは元と先のどちらも変更しない。容量不足の墓標回収は入る分だけを正確に移し、残りを墓標へ残す。
- 箱の解体・支持喪失・戦闘破壊でも装備の内容を移す。地面の予算が足りない場合は中身のある残骸/建物を残し、装備を消して成功扱いにしない。

## 旧保存の移行

旧セーブ、Generator1〜3、既存の建築・地形・保存バックアップを破棄しない。

1. 所持している同種群に既存の品質/耐久を適用する。現在の所持品にその品目がなく、現在の墓標にある場合は墓標へ結び付ける。
2. 継ぎ装は一つの消耗プールなので、1本だけへ移す。旧 `count` 本すべてへ複製しない。
3. より古い墓標や既存の地面/箱など、個体の来歴が保存されていなかった場所は個数を保持し、`legacy:true` と未記録の値で表す。存在しなかった履歴を復元したと主張しない。
4. 新しく作った装備と新規参加者の初期装備は品質1・満耐久・合成なしから開始する。墓標の古い個人辞書を参照しない。
5. 新形式で個数投影やID所有が矛盾する保存は拒否する。どちらか一方へ黙って合わせたり、余剰装備を捨てたりしない。

## 戦闘と投擲

攻撃/道具使用はスタミナ・矢・動作中条件を先に調べ、必要な個体分離をダメージや消耗より前に準備する。単に盾を持っているだけでは分離しない。使用中の個体をドロップ/収納/修理/合成して攻撃中に入れ替える操作は拒否する。別の未使用個体は移動できる。

投げた槍は共有の `gearFlights`（最大64件）が正本を持つ。飛行描画のProjectileには参照IDだけを持たせる。着地時は同じ装備を一度だけ地面へ移し、サーバー再起動時は保存された最終位置に回収可能なドロップへ戻す。地面の枠が足りない間は耐久保存された回収待ちレコードを残す。旧 `recover` 文字列は互換ヒントで、装備の所有権を持たない。

## 可視性とUI

個人のlotは本人のsnapshot/exportだけに含める。非公開の箱は個数とmetadataをまとめて隠す。共有された箱と地面に置いた装備の状態は、共同世界の品物として表示できる。

- 選択: `equip gear:<lotId>`
- ドロップ: `drop gear:<lotId>:<count>`
- 静的な箱: `store/take <boxId>|gear:<lotId>:<count>`

従来の品目名コマンドも選択個体を優先して扱う。防具は該当の装備枠を設定し、道具だけの個体選択で不正な武器IDへ変えない。未記録の旧metadataは画面で明示する。

## 検証

`equipment-items.test.ts` は純粋な移行・分離・移動・検証・合成トランザクションを扱う。`equipment-session.test.ts` は実Sessionの受け渡し、死亡→新品制作→墓標回収、同種別個体の修理/強化/合成、箱、私有export、失敗時の原子性、旧大量重複、Generator1〜3、槍の保存/復帰と戦闘中の移動を扱う。`equipment-websocket.test.ts` は独立した実2 WebSocketで受け渡し、重複コマンド、サーバー再起動、選択、他人の個人metadataがexportされないことを確認する。

公開ブラウザ、モバイル実機の選択/数量UI、全ゲーム長時間運用は別の受入項目。装備を移動倉庫へ許可する前には、その収納・破壊・設計再建経路まで同じ所有権処理へ統合する必要がある。
