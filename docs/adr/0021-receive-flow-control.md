# ADR 0021: 遅い受信者のための送信上限

状態: protocol7のローカル実装。公開受入は未実施。

## 背景

差分で帯域を減らしても、遅いクライアントへ無制限に送ると送信バッファが増える。Workersの標準WebSocket APIには、アプリが利用できる`bufferedAmount`が文書化されていないため、Nodeだけに依存する制御を採用しない。

## 決定

- 完全welcome、状態delta、個人exportに一回限りのランダム受領トークンを付ける。ゲームの権限や復帰用の秘密鍵とは別で、保存やURLへ残さない。
- クライアントは両方の差分を正しく復号した後に受領を返す。未来のtickを推測しただけの通知は受け付けない。
- 未確認の20件または2MiBで、その相手に対する新しいdelta生成を止める。基準/revisionは進めず、他の参加者と世界の権威処理は続ける。最新の正しい受領でそれ以前の送信も確認できる。
- 1通の大きなwelcome/exportは16MiBまで。従って送信待ちの上限は2MiBに最後の1通を加えた有限量となる。上限を超えた保存は消さず、サイズエラーで接続を閉じる。巨大な旧保存の分割初回転送はまだ未実装。
- 上限に達したまま10秒経過した接続は1013で閉じ、同じ本人IDと保存から再接続できる。サイズ超過1009は自動で無限再試行しない。
- export要求は一接続につき保留1件、最大5秒に1回に集約。resyncも送信可能になるまで保留する。
- packetを一度JSON化してサイズ計測し、その文字列をNode/Workerへ渡して再度のJSON化を避ける。
- pongが返っていても世界snapshotが12秒進まなければ、クライアントはonline状態を続けず再接続する。

## 検証

`delivery-window`は偽トークン拒否、件数/byte上限、累積受領と期限を確認。`coop-delivery-window`は相手一人が確認を止めても他方が進み、復帰時に差分が連続することを確認。

`coop-slow-reader`は独立した実2 WebSocketを接続する。片方が受領通知を止めると実際の送信数/byteが止まり、偽トークンでは再開せず、正しい受領で完全状態へ追いつく。再度止めて1013切断した後に、同じID・取得済み木材12個を保持して再参加する。これはアプリの受領制御試験で、OSのTCP受信窓や公開モバイル回線の性能試験とは区別する。

全体の固定checkoutでの型/単体/production build、公開2ブラウザの受入は別途確認する。CPU予算や一般的な公開サービスへのDDoS対策まで達成したとはしない。
