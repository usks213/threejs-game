# 帰還品を次の遠征につなぐ補給ループ

2026-10-07。110項目のうち、既存の権威サーバー・倉庫・帰還を使う限定された次の一周。
6商人、全体市場、アカウント共通経済、クエスト、全装備枠の完成ではない。

## 通常の流れ

1. 遠征で遺宝や灰銀鉱を拾い、生きて抽出する。
2. 全員の遠征が終わったら「補給所へ戻る」。鞄と倉庫を開く。
3. 自分の倉庫から帰還済みの遺宝・鉱石を選び、表示金額で売る。
4. 金貨で薬/包帯を購入。品物は倉庫へ届く。必要な武器と補給品だけを鞄へ移す。
5. 実際の携行武器と無料初期補給の有無を確認して準備完了にし、次の遠征へ出る。
6. 携行品は死亡で失う。消費した薬は帰還しても戻らない。売却/購入と残高は再接続後も残る。

金貨はゲーム内の値だけであり、実貨幣、課金、外部決済、購入可能な通貨ではない。

## 独自の価格と在庫

- 売却できるのは、自分の倉庫にある帰還済みの遺宝と鉱石だけ。
- 一回で選択したスタック全体を売却。価格は基準値×個数×（品質+1）。遺宝45、鉱石7。
- 赤灯の薬1個は12金貨、清潔な包帯1個は6金貨。必ず倉庫に届ける。
- 部屋の共有在庫は薬6個/包帯10個。次の遠征が実際に始まると補充される。
- 準備完了中、遠征中、結果から補給所へ戻る前は取引できない。
- 初期装備、盾、薬、包帯、鍵は買い取らない。無料装備を往復して金貨に変える抜け道を作らない。
- 金貨、本人の倉庫、直近6件の表示履歴は本人だけへ送る。在庫だけが部屋で共有される。

## 装備と保存

空の鞄だけが従来の無料初期キットを受ける。1品でも持ち込むと追加キットはない。
武器を含まない非空の鞄はサーバーとUIの両方で準備/開始を拒否する。
持ち込む武器は実際の鞄の先頭の武器で、ロビーの役割だけを変更して別の武器を生成しない。
複数装備スロットや役割ごとの熟練制限を完成扱いしない。

売買は権威サーバーの直列キューで確定。残高、品物、在庫、識別子の条件を全て確認してから
一括変更し、永続保存成功後にだけ通知/スナップショットを返す。古い操作連番の再送は拒否。
購入先が満杯、残高/在庫不足、対象違いなら品物・金貨・在庫は一切変更しない。
既存の品物IDに衝突する場合も購入を拒否する。

既存version1保存のshop未設定は初期在庫として読める。存在するshopが不正なら安全に拒否し、
倉庫を初期化しない。新しい保存キー、binding、migration、アクセス権は追加しない。
取引記録は既存receipt配列に最大128件を保持し、その直近6件を表示する。全期間の監査DBではない。
帰還結果の「保存した品数」はその遠征の携行品だけを数え、以前から倉庫にあった品を報酬に数えない。

## 検証と残件

重点単体は通常売却/購入、100回再送、初期装備の買い取り拒否、所有権、価格/数量偽装、
満杯、準備/遠征ロック、最終在庫への同時購入、保存失敗、JSON再起動、旧保存の互換読込を検証。
PC/Androidの通常入力ブラウザ経路は、遺宝の抽出→売却→複数購入→武器なし拒否→装備→
第二遠征で実被弾/購入薬消費→予定した死亡/携行品喪失→金貨と倉庫の再読込を検証する。
成功して生き帰る戦闘経路は別の全PvPvEゲートで保持する。実ブラウザ結果は公開後に確認する。

倉庫満杯時の抽出は従来どおり拒否される。報酬の受取待ち/拡張倉庫、6商人、売買対象の拡張、
クエスト/商人好感度、完全な経済監査、アカウント共通保存は未実装。


## 最初の公開試験で見つかった追加修正

5ba2cdf3は全1,411単体・型/build・配信SHA/health、WebKitと従来のPC/Android smokeに成功。
新しい両ブラウザ経路は実際の遺宝売却、複数購入、残高60/共有在庫/履歴、武器なし拒否と
第二遠征の正しい携行品まで通過した。間欠的な移動で敵より遅く逃げる試験経路は失敗した。
新しい補給試験は意図を明示した第二遠征の損失受入へ改め、購入薬の実回復/一回消費を
確認した後の死亡で、携行品だけが失われ銀行の品/金貨が保存されることを要求する。
既存の成功帰還を要求する全PvPvE試験を死亡許容には変更しない。

別の全PvPvE実行ではBが1008コードで拒否された。直接の理由は古いクライアントで
記録されておらず断定しないが、保存待ちキューが正しい50ms間隔の入力50件を同時刻に
数え直して切断するサーバー不具合を再現した。頻度制限の時計を受信時点へ移し、
40packet/12actionの元の制限は維持。遅い保存で正しい入力が切られず、本当の一斉floodは
従来どおり拒否される回帰試験を追加。既知の拒否理由だけをUIへ具体的に表示する。

## 通常入力の観測競合を修正

b23a0440は全1,416単体・型/build・公開に成功したが、補給受入は失敗した。
Androidのtraceでは第二遠征の精密な通過点を往復する間に攻撃を受け、PCでは
回復ボタンの描画安定待ち中に死亡していた。敵の知覚範囲に入った時点で移動を止め、
実被弾後に通常のQキーまたは事前に表示確認した回復ボタンの実タップを送る。
受信したサーバーsnapshotで購入薬の消失と体力の増加を同時に確認し、その後の死亡・
携行品喪失・倉庫/金貨保持を別々に要求する。体力付与や戦闘時間の変更は行わない。

同じ版の全PvPvE受入では、Bが132.9秒時点の観測直後、133.0秒に死亡してから
KeyTを送っていた。死亡で入力が止まる正しい動作に対し、存在しない攻撃の応答を
待って失敗した。この対人決闘の送信点だけは死亡snapshotも待機終了とする。
生存者の応答、対人kill、死体loot、生きた抽出、再接続保存、試験の240秒以内という
要求は保持する。再公開後の完全なブラウザ実行が成功するまでは受入完了としない。

11fab626の全1,418単体・型/build・公開・WebKitと全PvPvE受入は成功し、
生存抽出202.95秒と両者の再接続を確認した。補給受入だけは継続中。
PCは購入薬の実回復、死亡、金貨/倉庫保持まで通過したが、未開封死体の内容を
要求する誤ったassertionで失敗した。未開封の品物は意図してsnapshotから隠すため、
ブラウザは死体生成と非公開を確認し、購入薬消費後の正確な装備dropは追加単体で検証する。
Androidでは高水準tapの実行が4.875秒かかり、完了時には死亡画面へ移っていた。
被弾後の硬直終了を観測し、移動パッドと同じCDPの通常touchStart/endを回復ボタンへ
送る経路に統一する。薬の消費と実回復は引き続き必須で、失敗時も受信履歴を残す。

## 補給の公開受入と独立した戦闘ゲート

0170d80fは[CI37693708826](https://github.com/usks213/threejs-game/actions/runs/37693708826)で
全1,419単体、型/build、既存プレビューの同一SHA配信、WebKit、PC6件/Android6件に成功。
両環境で帰還品売却、有限在庫購入、武器条件、購入薬の実回復と一回消費、第二遠征の
携行品喪失、倉庫/金貨/取引履歴の再接続保持を確認した。補給所と死亡結果の実画像も検査済み。

独立した全PvPvE試験は中央の二体戦で失敗。traceでは69.95秒の重撃開始時に別の敵が
予備動作中で、盾の向きの外から70.15秒に被弾し、重撃の後隙中の71.35秒に再び被弾した。
次の重撃で相手を15HPまで減らした後、自分の後隙が終わる前に死亡した。
前版の生存抽出成功をこの実行の成功として扱わない。

次の受入ドライバーは、重撃の後隙に通常のS+Z入力で間合いを離し、30HP以下の敵には
通常攻撃Tで追撃する。敵へ向き直る間は前後移動せず、実際の入力とサーバー応答を用いる。
ゲームの敵/HP/被害/資源、四体討伐・対人・loot・生存抽出・240秒の条件は変更しない。
この修正の厳密なブラウザ受入は再公開後に確認する。
