# 協力プレイの描画待ちと更新時計

2026-10-05。対象は PR #4 の公開二人プレイ受入。main の変更なし。

## 確認できた現象

公開コミット `81f3dbb6bd064acc317a42ab7826d0a077bfee69`、CI ジョブ
`111723097381` のトレースでは、参加・チャット保持・送信は成功した。
ゲストの「探索に戻る」後、実 KeyD の移動は 60 秒以内に 0.65 m に届かなかった。

- ゲストの通常の観測呼出しは約 10–26 ms。その後の一回は 53.1 秒待った。
- その間の描画回数は 2 → 4。performance パスの平均描画呼出しは 12,830.7 ms。
- 同期フレームの鮮度が切れ、ゲストは安全のため操作送信を止めた。
- この壁時計の空白だけでは、GPU、スナップショット復元、CPU 競合それぞれの寄与は確定できない。

以前はシミュレーション・通信・描画を同じ RAF コールバックで実行していた。
描画しないメニュー中のホストも、共有ブラウザーの compositor が RAF を遅らせると
ワールド更新とフレーム送信を遅らせる構造だった。

## 変更

- 可視の部屋セッション中だけ、単一のタイマーにシミュレーションと通信更新を持たせる。
  RAF は描画担当。単独プレイの更新は従来どおり RAF。
- 可視性、縦画面、Pause、ゲストの非権威性、1 回 0.1 秒・最大 6 固定 tick の上限は保持。
  メニュー中のホスト継続と、非表示タブのシミュレーション停止を区別する。
- performance 画質の新しい可視シェーダーを Three.js の compileAsync で準備してから描画する。
  非表示の空は準備せず、実際の灯り・霧・環境を使う。待機中は再メッシュを繰り返さない。
  画質変更も明示的な再描画を要求する。物理・地形メッシュ・描画品質設定は削らない。
- 読み取り専用観測に更新間隔/CPU 時間、描画呼出し時間、シェーダー待ち、
  スナップショット適用時間、入力送信数、フレーム鮮度、入力軸と可視状態を追加。
  高頻度の移動検査は terrain raycast/セーブ複製を含まない観測を読む。

独立タイマーも、同じ JavaScript スレッドを占有する同期処理中には走れない。
非同期シェーダー準備も、ドライバーの描画・バッファー転送をすべて非同期にはしない。
これらを隠すための時限延長、移動付与、精度/距離緩和はしない。

## 検証と残り

単体試験は、RAF が一度も来ない場合の部屋更新、二重 tick 防止、単独時計、
遷移、停止/例外後の後始末、非表示/縦画面/メニュー/ゲスト境界、
シェーダー準備待ち・可視化・版変更・灯り変更・失敗を検査する。
3 秒の鮮度期限と、非アクティブ時の中立入力も固定条件で検査する。

二人の実ブラウザー受入は次の統合 SHA の CI で再検証が必要。
ローカル Chromium は起動時の socket EPERM で使用できず、起動フラグ変更や
権限迂回で代用していない。新しい観測で残る待ち時間の内訳を確認する。
