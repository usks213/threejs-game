# PR #3: 地形の背景処理とスマホUI

## ユーザーが指摘したブロッカー

- 動作が重く、まともに遊べない。
- 地形生成/ロードが操作やゲーム進行を止める。
- スマホの複数の操作ボタンが重なる。

前のCI成功は、この実機での不具合を解決した証拠ではない。

## 原因と変更

### 背景処理

以前もWorkerはあったが、ゲームの30Hzシミュレーションと `meshBrick` が同じスレッドで動いていた。8msで処理ループを区切っても、1個のメッシュ生成が長い場合は中断できず、入力/物理を止める。

今回はシミュレーションとは別の専用Terrain Workerを1本追加。モバイルでワーカーを無制限に増やさず、1ジョブずつ距離/編集優先で処理する。地形の差分だけを増分で同期し、各ジョブのepoch/versionを照合。編集、範囲外への移動、再ロードで古い結果を使わない。新規ワールド読み込み時は旧子Workerを停止する。

Worker間はfine/coarse/grassのTypedArrayを転送し、複製しない。相対座標化、境界球、草の配置点生成も背景側で済ませる。ゲーム側のメッセージ受信では描画メッシュを作らずキューへ入れる。実際に描画するフレームにだけ最大2チャンク、512KiB、soft 2msで適用し、描画へ送信した後にクレジットを返し、未消費4メッシュで生成側へバックプレッシャーを掛ける。メニューで描画しない間にGPUアップロードを溜めない。描画していない空チャンクの削除はキューに積まず、実際の削除はアップロードとは別の個数上限で処理する。1つの不可分なアップロードが2msを超える可能性は残るため、hardなフレーム時間保証とは呼ばない。

描画/物理のVoxel寸法やHDR機能は削除しない。GPU-driven化したという主張はせず、今回の経路はCPUのマルチスレッド化。Voxel照準/遮蔽は固定間隔の全距離走査から境界判定付きDDAへ替える。

### UI

以前のGrid指定に、古い `position:absolute` が各ボタンへ残り、Gridの配置が効いていなかった。縦持ちを横画面へ回転しているのに物理画面のmedia queryを使う箇所もあった。

配置を一本化する。左は移動/走行、右は2列×3段の操作Grid、中央下は8クイックスロット。狭い横画面ではクイックスロットを4列×2段にし、照準操作/解体をその上へ置く。建築操作は別の中央上部Grid。ダイアログ中は背後のゲーム操作を隠す。Safe Areaと論理Viewportのcontainer queryを使用し、48px以上のタップ対象を維持する。

## 比較測定

`node scripts/benchmark-terrain-streaming.mjs 64`

同じgenerator-3、0.5m、64ブリック、118,943三角形。4ブリックのウォームアップ後に実GameSimulation.stepを30Hzで回す。Worker起動と初期化は測定外。水/物体を空にして地形メッシュの競合を分離する。

2026-10-04の再現測定（Node v24.19.0 / AMD EPYC）:

- 最大シミュレーションTick間隔: 59.13 → 34.16ms
- p95 Tick間隔: 56.38 → 33.79ms
- 最大イベントループ遅延: 32.76 → 3.02ms

これはクラウドCPUの合成比較であり、スマホFPS/GPU時間/全ゲームの品質証明ではない。実機でまだ重い場合はフレーム/GPUコストを測って次のボトルネックを切り分ける。

## 実操作チェックで見つかった追加修正

3e56d0fのUI矩形/タップ検査（4サイズ×14状態）は成功したが、実操作チェックは完了扱いにしない。再読み込み時に遠方の継続ストリームまで待つ条件と、縦横往復で変形済み要素がモバイルのinnerWidth/innerHeightを膨らませる問題が出た。

- 近傍のready通知を受けた時点のキューだけをフェンスにする。後から届く遠方メッシュはゲーム開始を妨げない。
- 初期メッシュのGPU送信は軽い通常描画で行い、状態が届く前のHDR合成を繰り返さない。プレイ時のHDR機能は維持する。
- 回転/入力/描画の寸法は固定されたdocumentElement.clientWidth/clientHeightで統一。bodyを固定し、回転したゲームがlayout viewportを広げない。

## 水処理の追加最適化

重力テストだけを軽くして問題を隠さず、初期河川を含む実GameSimulationの60tick×2地点を測定した。水の全セル走査/並べ替え、容量参照、障害物の三角関数/小配列割当を減らした。セルの近傍選択と同距離時の順序、2048/8192の予算、遠方保存、流量/速度/障害物マスクは維持する。

同一河川のpaired CPU測定:
- spawn 水更新平均27.92→9.79ms、最初のcold更新117.64→48.39ms
- 河岸 水更新平均25.64→7.91ms、cold更新70.68→31.07ms
- 表示snapshot平均8.36→5.01ms / 11.15→6.12ms
- 総12865セル、最終水量1508.473632812502、表示頂点20088/25158は一致

水面メッシュも専用Workerへ移し、1件の処理/結果クレジット＋最新snapshot1件に制限。描画直前に結果を消費してから次を送る。入力Float64/結果Float32は使用分だけ転送/再利用し、旧epoch・古い応答・破棄後の応答を使用しない。

同じ8192セルで旧メイン計算平均10.564msに対し、新メインの入力整形＋GPU用配列コピーは平均0.1451ms（p95 0.2903ms）。形状/法線/色は完全一致。これはworker計算/転送待ち/GPU描画を含めたFPSではない。CPUのcold31–48msや実機GPUの負荷は残るため、完全にヒッチがなくなったとは主張しない。

証拠: `docs/benchmarks/water-cpu-2026-10-04.json`, `water-meshing-2026-10-04.json`。
再現: `node --import tsx scripts/profile-fluid.ts` / `node --import tsx scripts/profile-water-meshing.ts`。

## 移動時の数秒停止に対するストリーム/描画修正

JSでBufferGeometryを作るだけではGPU転送は済まない。画面外の形状や未使用LODは、移動で初めて見えた時にgl.bufferDataが集中する。新しい受入キューは1×1のoffscreenゼロ三角形パスでfine/coarseの全頂点属性とindexを事前送信してから公開する。色/深度を書かず、レンダーターゲット/影/XR/drawRangeを復元。同期GPU readbackは使わない。計測は「GPU完了時間」でなく転送コマンドの送信に掛かったCPU時間。

16m境界で160ブリックが入れ替わるため、完了済みの地形だけを1チャンクの非表示haloに保持（最大768追加エントリ/16MiB）。Worker側も32MiB/2048件のキャッシュを持つ。編集対象、サンプリング変更、world epochの変更で無効化する。通常の要求範囲以外は描画/照準から除外し、画面の幾何量を増やさない。

同じx=16境界を6回跨ぐ比較: 生成960→160件、各Worker hopの転送10,477,368→1,514,700 bytes。最初の跨ぎ以降の5回はジョブ/転送とも0。同じ要求範囲の三角形数を維持。Nodeの生成＋二段転送は4558→640ms。GPU時間/実機FPSではない。

`docs/benchmarks/terrain-boundary-2026-10-04.json` と `scripts/benchmark-terrain-boundary.mjs` に再現条件を記録。初めて訪れる範囲の生成は引き続き必要。

照準は到達距離に合わせて有限化し、ブリックAABBで落としてから三角形を調べる。RAF間隔、world更新、カメラ/操作raycast、草更新、実render呼び出し、HDRの大気更新/composerを分けて記録する。Worker heartbeatの改善だけで移動停止が解消したと判定しない。短い境界移動テストは2秒以上のフレーム停止と入力停止を検査し、CIソフトウェアGPUの値を電話のFPS目標にはしない。

三角形を直接SDF描画へ全面置換してはいない。現在のdensityは厳密な距離場ではなく、単純なsphere tracingへ変更すると穴/見落としが起こりうる。GPU feedbackやVisibility Bufferは別設計として検討し、即時の停止対策を全面再実装待ちにしない。
